## 先重現問題

```bash
node ask.ts "期末成果發表會每組報告幾分鐘？"
```

它只能給你**一般性的猜測**——「常見範圍是 5 到 15 分鐘」「建議查看課程大綱」。
實測結果就長這樣，而正確答案是 **8 分鐘 + 4 分鐘問答**。

對產品來說，這種答案跟答錯一樣沒用：使用者問了，你什麼都沒給。

### ⚠️ 這裡有個坑，值得先講

`ask.ts` 的對照組做了兩件事，缺一不可：

1. **在空目錄裡跑**
2. **明講「不要去讀任何檔案」**

因為 **pi 是 agent，它有 `grep` / `find`**。少了第 2 點，它會自己去整個檔案系統
把 `knowledge/club-handbook.md` 翻出來——然後你會以為「它本來就知道」。

實測時它真的這樣做了，還順手引用了檔案路徑。

**這本身就是一課**：agent 拿得到資料的方式不只 RAG，
「讓它自己去找」往往更簡單——這正是節 1 地圖第一列講的事。

## 檢索是怎麼做到的

`retrieve.ts` 裡有**兩個版本**，改 `MODE` 那一行就能切換：

```ts
const MODE: "keyword" | "naive" = "keyword";
```

| 版本 | 做法 | 結果 |
| --- | --- | --- |
| `naive` | 檢查**整句問題**有沒有原封不動出現在段落裡 | **四題全部撈不到** |
| `keyword` | 把問題切成 **2 字一組**，數有幾組命中 | 四題都撈到了 |

**把 `MODE` 改成 `"naive"` 跑一次 `node check-retrieval.ts`，你會看到全部 ✗。**
改回 `"keyword"` 再跑一次。這就是「切」跟「沒切」的差別。

### 為什麼是 2 個字一組

中文沒有空格，**沒辦法用 `split(" ")` 斷詞**。真的斷詞要套 jieba 那類工具，太重了。
所以用最粗暴的辦法：

```
「報告幾分鐘」→  報告、告幾、幾分、分鐘
```

然後數這幾組有幾個出現在段落裡。粗暴，但對中文意外地有效——
而且它讓你看到：**檢索沒有魔法，就是在數字面上的命中。**

## 驗收

**基礎**　你能展示同一個問題的兩種答案，而且第二種是對的，
並且說得出 `naive` 跟 `keyword` 差在哪。

**進階**　做下面的「[關鍵字檢索的極限](#進階關鍵字檢索的極限)」——
找出那一題「正確段落跟錯誤段落同分」的，並說得出為什麼。

多試幾個問題：

- 器材可以借幾天？
- 社辦鑰匙有幾副？
- 單筆支出超過多少要開社員大會？
- 社團專案的補助上限是多少？

## 進階：關鍵字檢索的極限

試試這兩個問題：

```bash
node ask.ts --rag "器材可以借幾天？"
node ask.ts --rag "缺席太多會怎樣？"
```

看一下它檢索到哪幾段、分數多少。你會發現**正確的段落跟錯誤的段落分數一樣高**。

原因：關鍵字比對只看**字面**。手冊裡寫「借用期限」，你問「可以借幾天」，
字面上只重疊了一個「借」字。

**進階題**：改成 embedding 檢索，比較兩者在這類問題上的差異。

> ⚠️ 免費模型不一定提供 embedding。如果沒有，改用 TF-IDF 或 BM25
> ——一樣是純本地、不用呼叫 API，而且已經比 2-gram 好很多。
> 重點不是用哪個演算法，是**看見「字面比對」的極限在哪**。
