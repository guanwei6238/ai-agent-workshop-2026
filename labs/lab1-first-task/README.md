# Lab 1：用 agent 做一個真的功能

> **目標**：體感「派工」跟「問答」的差別，並且**用檢核表驗證它到底做到了什麼**。

## 素材

`habit/` 是一個能跑的小 CLI。它的風格很明確——但**沒有寫成任何文件**。

先花 3 分鐘跑起來、翻一下 `src/`：

```bash
cd habit
node init.ts          # 變成 git repo + 產生種子資料
node src/cli.ts list
```

## 先讀規格書

**[`SPEC.md`](SPEC.md) 是你要 agent 做出來的東西。先讀完再開始。**

裡面寫清楚了功能、使用方法、邊界、以及「不要做的事」。
`verify.ts` 會照這份規格逐項檢查。

## 步驟

### 1. 開 pi，選模型

```bash
cd habit
pi
```

進去之後打 `/model`，選 `nemotron-3.5-lightning-free`。

> **用互動模式，不要用 `pi -p`。** 互動模式會顯示它呼叫了哪些工具、
> 讀了哪些檔、跑了什麼指令——那是 agent 跟網頁版最不一樣的地方。

### 2. 第一次：隨便講

**用你平常跟網頁版講話的方式**，不要照規格念。例如：

> 幫我加一個 streak 指令

### 3. 看著它做，然後看 diff

```bash
git diff
```

### 4. 跑檢核

```bash 
node ../verify.ts
```

把結果填進 [`checklist.md`](checklist.md) 的第一欄。

### 5. 第二次：把規格變成 prompt ← 這步是重點

```bash
node restore.ts                  # 程式碼 + 資料一起還原
```

**看第 1 次哪幾項沒過，那些就是你要補進 prompt 的東西。**
`SPEC.md` 已經寫得很清楚了，你的任務是**把它變成一段 prompt**。

而「變成 prompt」有**兩種給法**，你要選一種：

| | 怎麼做 | 你在決定什麼 |
| --- | --- | --- |
| **A 貼進去** | 把 `SPEC.md` 的內容抄進你的 prompt | **它看到什麼** |
| **B 指過去** | prompt 裡寫「先讀 `../SPEC.md`」 | **它去哪裡找** |

> 兩種都會動（B 實測可行，pi 讀得到上一層的檔）。
> **這兩種都叫 context engineering** —— 第 1 次你兩種都沒做，
> 只給了一句話，剩下的 context 全是它自己 `ls` + `read` 湊出來的。

再跑一次 `node ../verify.ts`，填第二欄。

> **做完基礎的可以試另一種給法**，看檢核表分數有沒有差。
> 沒差也是結果——那代表這個規格夠短，兩種給法沒有區別。
> （規格如果是 50 頁，答案就會完全不同——那是節 3 RAG 的題目。）

## 驗收

**基礎**　第 2 次的通過項目**明顯多於**第 1 次，而且你說得出差在哪幾項。

**進階**　試試看能不能用**最短的** prompt 拿到 14/14。
（提示：規格裡有些條目是「不要做什麼」，那種最容易漏。）

## 參考：實測過的結果

用 `nemotron-3.5-lightning-free` 實際跑出來的：

| | 通過 | 主要問題 |
| --- | --- | --- |
| 隨便講（「幫我加一個 streak 指令」） | **5 / 14** | 要吃參數（規格是列出全部）、**算成「最長」連續而不是「目前」**、自己用 `new Date()` 重寫日期運算 |
| 照規格講 | **13 / 14** | 只剩一個沒用到的 import |

**注意風格層它幾乎都跟上了**（開在 `commands/`、有註冊、用 `ui.ts`、沒用 `any`），
**兩次的差距幾乎全在規格層**——它做的東西跟你要的不一樣。

> 你的結果不一定跟這裡一樣（模型每次不保證相同），但**差距的方向會一樣**。
