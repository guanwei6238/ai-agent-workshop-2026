# Lab 3：給 agent 一雙手

> **目標**：親手給 agent 一個它本來沒有的能力，
> 然後證明 **`description` 寫得好不好，決定它會不會用**。

前面兩個 lab 都在「說給模型聽」——`AGENTS.md` 是請求，skill 是說明書。
這個 lab 是第一個 **真的會去執行** 的東西。

## 素材

```
lab3-tools/
├── club-tool.ts        ← 你要改的（3 個 TODO，都在上半部）
├── solution/           ← 參考解，卡住再看
├── workspace/          ← ★ 一定要在這裡面跑 pi ★
└── verify.ts
```

> **為什麼要在 `workspace/` 裡跑？**
> agent 有讀檔工具。資料如果放在它看得到的地方，它會**直接去讀檔**，
> 那就試不出工具有沒有被呼叫了。所以資料寫死在 `club-tool.ts` 裡，
> 而你在一個空目錄裡問它。

## 步驟

### 1. 對照組：它現在答不出來

```bash
cd workspace
pi --provider opencode --model mimo-v2.5-free
```

輸入：

```
我等一下想去社辦寫 code，E205 現在方便嗎？
```

它會反問你 E205 是什麼。**把回答記下來**，然後 `/quit`。

### 2. 載入工具——但它還是不會用

`club-tool.ts` 已經是可以跑的了，先原封不動載進去：

```bash
pi -e ../club-tool.ts --provider opencode --model mimo-v2.5-free
```

**輸入同一句話**：

```
我等一下想去社辦寫 code，E205 現在方便嗎？
```

**工具就在那裡，但它多半還是答不出來。**

為什麼？看一眼 `club-tool.ts`：

```ts
name: "tool_a",
description: "一個工具。",
parameters: { room: { type: "string", description: "參數" } },
```

模型看得到的只有這三樣。**這三樣都沒有告訴它「什麼時候該用」。**

### 3. 把三個 TODO 改好 ← 這一步是重點

回去改 `club-tool.ts`：

| TODO | 改什麼 | 判斷標準 |
| --- | --- | --- |
| 1 `name` | 取一個看得出用途的名字 | 只能小寫英文、數字、底線 |
| 2 `description` | **寫清楚「查得到什麼」＋「什麼時候用」** | 這一項影響最大 |
| 3 `parameters` 的 description | 說清楚這個參數是什麼、舉個例 | |

改完再跑一次**同一句話**：

```bash
node verify.ts
```

通過的話會長這樣：

```
E205 目前 3 人在裡面，鑰匙歸器材長管理，借用期限到 21:00。
✓ 工具被呼叫了 —— 回答裡出現了只有工具查得到的資料
```

`3 人 / 器材長 / 21:00` 只存在於 `club-tool.ts` 的資料裡。
它講得出來，就代表**工具真的被執行了**。

### 4. 進階：讓它「做」，不只是「查」

在**同一個檔案裡**再註冊一個 `club_book_room`，收 `room` 和 `hours`，
把借用登記起來（存在一個變數裡就好，不用真的寫檔）。

> ⚠️ **第一個工具要留著。** 兩個工具都註冊，才試得出「模型會不會挑對」。

description 的寫法跟 TODO 2 同一個原則，但多寫一句話：
**講明這個動作會實際改變狀態**，不是查詢。

改完這樣試：

```bash
cd workspace
pi -e ../club-tool.ts --provider opencode --model mimo-v2.5-free
```

依序輸入這三句，**重點是第三句**：

| 你說 | 預期它做什麼 |
| --- | --- |
| `E204 現在方便嗎？` | 呼叫 `club_room_status`，回「現在沒有人」 |
| `幫我把 E204 借兩個小時。` | 呼叫 `club_book_room`，回登記成功 |
| `E204 現在方便嗎？` | 再呼叫 `club_room_status` —— **這次會多出借用時間** |

**第三句答得不一樣，就證明狀態真的被改掉了。**
如果三句都只呼叫同一個工具，那是 description 沒把兩者分開。

> **參考解**：`solution/club-tool-advanced.ts`（兩個工具都在裡面）。
> 一樣先自己試過再看。
>
> ```bash
> pi -e ../solution/club-tool-advanced.ts --provider opencode --model mimo-v2.5-free
> ```

**這時候你就給了 agent 一個會改變狀態的能力。**
`AGENTS.md` 寫「不要亂借教室」擋不住這件事——那是節 2-F 守衛的題目。

## 驗收

**基礎**　你能展示步驟 1、2、3 的三種回答，並說得出第 2 步為什麼失敗。

**進階**　完成步驟 4，並說明「查」跟「做」在權限上的差別。

## 這個 lab 跟 MCP 的關係

你剛剛做的事，跟 MCP 想解決的問題**一模一樣**：給 agent 一個它本來沒有的能力。

| | 你剛剛做的 | MCP |
| --- | --- | --- |
| 要跑額外的進程 | 不用 | 要 |
| 跨工具通用 | 不行，綁 pi | **可以，這就是 MCP 的重點** |
| 上手成本 | 低 | 中 |
| 適合 | 只有你自己要用 | 要給別人／別的工具用 |

MCP 的價值在「**標準**」：寫一次 server，所有支援 MCP 的工具都能接。
如果只是要給自己的 agent 加個能力，直接寫 tool 更快。

pi 核心刻意不內建 MCP，要另外裝 extension——`../appendix-mcp/` 有課後自習的路線。

## 一句話帶走

> **`description` 是寫給模型看的，不是寫給人看的。**
>
> 這件事跟 skill 的 `description` 是同一個坑，跟節 3「寫給模型看跟寫給人看不一樣」也是同一件事。
>
> 而且**工具沒被呼叫不是「失敗」**——它沒壞也沒報錯，是模型判斷這件事跟它無關。
> 對系統來說什麼事都沒發生，**所以你不會收到任何錯誤訊息**。
